## 结论

字段 `parser + 0x11d` 在每个新文件处理开始时于 `0043dd1c` 清零（反编译行 30987–30994）。它在段落后处理函数 `00437374` 中有条件地置 1（行 27917–27985），并由运行片段分类函数 `004098f8` 读取以门控字号计数（行 4127–4174）。在主要文本运行路径 `004120b8` 中，顺序是 `004098f8` 后接 `00437374`（行 8087–8102）；格式解析路径 `0040e9a8` 也按此顺序调用二者（行 6947–6955）。因此这是跨运行/段落阶段的解析状态：本运行到来时读当前值，后续段落处理可能启用它，之后维持到新文件重置。

`00437374` 首次启用时要求当前标志为 0 且 `parser + 0x120` 为 0（反编译行 27917–27920）；若检查的 token 比较满足其一，或剩余文本长度大于 60，则置 `+0x11d` 和相邻 `+0x11e` 为 1（行 27940–27984）。启用后本函数没有清除此标志。全反编译文本中只找到两处 `+0x11d` 写入：文件处理初始化写 0，以及这里写 1。

直接调用关系还显示 `0040e9a8` 与 `004120b8` 都调用 `004098f8` 和 `00437374`；另有段落/结构解析函数直接调用 `00437374`，见 `calls.tsv`。这支持“共享解析状态并被多个解析上下文推进”的描述，但不足以确认 `+0x120`、`param_3+0xac`、`parser+0xc8` 的源码级角色名称。尤其不能仅凭偏移断言它们就是通用 table/textbox 标志。已存在的字号索引也明确将 AC、C8 的完整语义列为未知。

## 表格与文本框边界

静态上可确认：`+0x11d` 是解析器实例上的状态字节；表格/文本框相关路径如果复用该实例，已置位的值不会在 `00437374` 内被清掉。首次启用则受 `+0x120 == 0` 守卫限制；字号生产器还分别检查运行属性 `param_3+0xac`、`param_1+0xc8`、`param_1+0xf0` 和 `param_1+0x110`，这些条件会影响具体字号计数分支，但不写回 `+0x11d`。现有证据不足以把各字段完整命名为表格或文本框角色，也不足以声称所有这类上下文都共享同一状态实例。

# 原生232图片判据与版本隔离

v0.2.11 为 `Pic.PixelSizeTooLarge` 增加独立232证据。当前仅验证博士NKR的两个上下文：单张普通内嵌RGB8 PNG的DOCX，以及单页、未旋转、内嵌Times New Roman/ToUnicode并含一张RGB8 PNG的PDF。图片像素乘积需小于2³¹；矢量、透明图片、重复摆放、其他模式不提升验证状态。

实际判据是有符号32位乘积严格大于16,000,000。3999×4000、4000×4000未走超限分支，4001×4000走超限分支。DOCX虚表+0x24/+0x30在已测PNG上分别返回高度/宽度。已观察输出标志0/1和共享报告计数0/1；PDF也命中其独立比较和输出分支。计算阈值不是学校的图片清晰度标准。

业务地图与分析伪代码：`evidence/business-map-232/pixel-function-map-r1/`。分析名称不是原作者符号。核心地址包括DOCX比较0042ae4e、PDF比较00472be7、报告计数0047c709；共享文件入口仍为0047a528。完整边界在 `pixel-boundaries-r1/`，独立复核在 `pixel-audit-r2/audit.json`。

本机剩余乱码来自CP1251的独立ANSI字面量，在005746f5返回点观察到显式936转换。原生包装器现在默认开启精确输入哈希、调用点及原代码页检查，只将该字面量的0/936实参改为1251。它没有替换输出报告文本。保留同输入控制/处理记录；处理后仅单位文字变化，原诊断与俄语环境历史记录相同。需要复现未修正对照时使用 `--preserve-pixel-codepage --trace-images`。

规则注册表的 `verification_by_context` 继续描述旧230证据，`verification_by_build["232"]` 描述新的版本限定证据。报告只在精确版本、格式、模式、图像配置、策略和源码/证据哈希均符合时提升该项验证状态。232其他规则不因此升级；缺失证明或哈希变化会回到待复核。

PDF资源别名现在按同一页面与XObject去重，真实摆放位置仍保留在 `bboxes`；一图重复摆放不属于已验收配置。图片数量不再因为两个名称指向一个对象而翻倍。

自动修复范围不变，不自动压缩、重采样、删除或替换图片。仍需原EXE运行原生参考；独立引擎只取得这一判据的有限版本证据。

下一项明确差异：静态代码中的图片文件大小判据读取ZIP本地头未压缩条目大小，与本地累计图片字节模型不同，且代码30,000,000与报告“40Mb”不一致。尚待动态边界验证，不改变该规则。

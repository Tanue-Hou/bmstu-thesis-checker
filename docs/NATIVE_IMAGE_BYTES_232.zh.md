# 原生232图片字节大小判据

`Pic.FileSizeTooLarge` 在232 DOCX中的实际判据是：对被引用的图片逐项查ZIP本地文件头，读取偏移0x16的无符号32位未压缩大小字段，严格大于30,000,000字节时累计图片上下文；不是图片总量、压缩包大小、中央目录大小或解码像素内存。

原程序诊断文字独立写着“больше 40 Mb”。为保留原生对照，俄语文案沿用40 Mb，但JSON明确提供真实比较阈值30000000 bytes、每图声明大小、计数、ZIP条目、绘图XML位置和关系ID。中文说明不会把40MB当作已验证阈值。该提示没有防查重含义，也不能直接作为学校违规结论。

五个合成博士NKR DOCX已实际运行，断点记录包含本地头字段、返回值、无符号比较、触发分支和报告计数：

| 输入 | 原生读取值 | 原生计数 |
|---|---:|---:|
| 单图29,999,999字节 | 29,999,999 | 0 |
| 单图30,000,000字节 | 30,000,000 | 0 |
| 单图30,000,001字节 | 30,000,001 | 1 |
| 两图各22,000,000字节 | 各22,000,000 | 0 |
| 流式ZIP图片实际30,000,001字节，本地头为0 | 0 | 0 |

图片是有效RGB8 PNG，在IEND后增加无害填充以隔离字节大小与像素数；ZIP字段没有伪造，CRC验证通过。流式ZIP通过标准data descriptor写入。原生只是读到本地字段0，不能把它解释成图片实际没有数据。

本地232 DOCX引擎已改为上述逐图判据，纠正了累计40MiB模型的一个误报反例和一个漏报反例；这不是实际论文准确率统计。旧230/PDF本地策略保留为未验证历史行为，不声称原生230也如此。

新增验证上下文仅为232/docx:phd，配置限1–2张普通内嵌RGB8 PNG、标准ZIP压缩方法8、flags0/8。ZIP64、重复条目、异常本地头、矢量、其他模式仍待验证。源码和证据哈希均须吻合，旧像素规则的实现哈希在复核后同步刷新。

业务地图与分析伪代码在 `evidence/business-map-232/image-bytes-function-map-r1/`；实际边界在 `image-bytes-boundaries-r1/`，独立审计在 `image-bytes-audit-r1/audit.json`，同输入MCP验证在 `image-bytes-mcp-r1/`。旧像素地图中的“字节大小尚待验证”是历史状态。

CLI原生追踪参数 `--trace-image-bytes` 只加观察断点，不修改大小或分支。自动修复权限不扩大；不自动删除图片或重采样。

仍待恢复的部分：完整形状过滤、查找失败哨兵ffffffff、ZIP64和异常头路径、其他类型及模式、为何文字标40Mb。当前还不是完整独立复刻。
